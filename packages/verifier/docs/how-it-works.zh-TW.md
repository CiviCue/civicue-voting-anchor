# 驗證原理

[English](how-it-works.md) | **繁體中文**

> 本文件譯自英文版。若兩者有出入，以英文版為準。

本文件說明為什麼驗證工具給出的 PASS 值得信任：平台承諾了什麼、為什麼事後無法更改這份承諾，以及為什麼驗證工具不必信任平台就能檢查它。如何執行驗證工具，請見 [CLI 使用指南](cli.zh-TW.md)。

## 驗證的主張

投票場次結束後，CiviCue 平台會公開該場次的（匿名化）選票與結果。PASS 確立兩件事：

1. **完整性：** 公開的選票與結果自錨定上鏈以來都沒有被更改過。
2. **正確性：** 這個結果是公開的選票依照該場次投票方式（多數決、平方投票或排序複選）計算出的正確結果。

## 各方掌控什麼

| 角色                       | 掌控範圍                                                                            | 驗證工具信任它的部分                                     |
| -------------------------- | ----------------------------------------------------------------------------------- | -------------------------------------------------------- |
| CiviCue 平台（閉源）       | 投票本身、公開的資料集、metadata API，以及執行錨定的 relayer 金鑰。                 | 完全不信任。它提供的每個值都會被重新計算，或與鏈上比對。 |
| Base 上的 `AnchorRegistry` | 每個場次一筆只能寫入一次的 `(merkleRoot, tallyHash, timestamp, blockNumber)` 紀錄。 | 承諾的內容，以及承諾的時間。                             |
| 本驗證工具（開源）         | 重新計算的過程：標準形式、雜湊，以及各投票方式的計票規則。                          | 它自己。任何人都可以閱讀、執行和重新實作。               |

驗證工具把平台視為潛在的對手。它唯一不經檢查就從平台取得的，是要去**哪裡**找：registry 地址與資料集 URL。兩者都可以覆寫（`--contract`、`--dataset-url`）。資料集 URL 錯了會得到 FAIL；registry 地址則可以與公開的部署紀錄比對（見[確認 registry 地址](cli.zh-TW.md#確認-registry-地址)）。

## 開源與閉源的分界

平台是閉源的，這個 repo 是開源的。平台**產生**的東西，開源這一側都能**獨立重現**：

| 閉源（CiviCue 平台）                                           | 開源（本 repo）                          |
| -------------------------------------------------------------- | ---------------------------------------- |
| 投票引擎、身分與投票資格                                       | Base 上的合約 `AnchorRegistry`           |
| 收集選票並匿名化成資料集                                       | [標準格式](canonical-schema-v1.zh-TW.md) |
| 計算計票結果與承諾                                             | 依投票方式重新計票、重建 Merkle tree     |
| 提供[驗證 API](verification-api.zh-TW.md)，並透過 relayer 錨定 | 驗證工具的函式庫與 CLI                   |

雙方唯一共用、且攸關信任的東西是標準格式和它的雜湊規則，而這兩者都是公開的。PASS 的意義不需要信任閉源這一側的任何東西。

## 承諾是怎麼產生的

場次結束時，平台會從選票算出兩個 32 位元組的雜湊，寫進 registry。每個步驟都由[標準選票格式](canonical-schema-v1.zh-TW.md)定義。以下用 `vectors/v1/quadratic/basic.json` 這個場次完整走一遍（3 位投票者、預算 10 點 voice credits、選項 A、B、C）。

**1. 把每張選票正規化，並序列化成標準 JSON。** key 經過排序、沒有空白，值為 0 的分配會被移除：

```text
{"allocations":{"A":2,"B":1},"voter":1}
{"allocations":{"C":3},"voter":2}
{"allocations":{"A":1,"B":1,"C":2},"voter":3}
```

**2. 把每張選票雜湊成一個 leaf**，前面加上 schema 標籤：

```text
leaf = keccak256("civicue.ballot.v1" ‖ 0x00 ‖ canonicalJson(row))

leaf1 = 0x57eb90783a839e6f13052b7377df13156ad96862cc03212ee625420938b16123
leaf2 = 0xd59a242e2950fb5c58ddfaf23634098fc845cb92081f609387bf30af051ba5f7
leaf3 = 0x16837d525a4e1eb9244012de1abb9ccfbe614b6c92cb0af5a6a9c7bf305eabec
```

**3. 依投票者順序，用這些 leaf 建出 Merkle tree。** 落單的 leaf 原封不動地往上一層：

```text
node = keccak256(0x01 ‖ left ‖ right)

n12        = node(leaf1, leaf2) = 0x638e5e4225fd6679a560f363b48b2b3db8d7c1104c2b925424a239fa2e6dffe7
merkleRoot = node(n12, leaf3)   = 0x39e8eb44d1f1c0ed4da7c2dd465162f7962c6bf2db7a4bb5f4817e5d1a06ffa5
```

**4. 依投票方式計票，並把標準計票結果雜湊。** 每張選票都在預算內（2²+1² = 5、3² = 9、1²+1²+2² = 6，都 ≤ 10）：

```text
{"ballotCount":3,"schemaVersion":1,"totals":{"A":3,"B":2,"C":5},"voiceCredits":10,"votingMethod":"QUADRATIC","winners":["C"]}

tallyHash = keccak256(canonicalJson(tally)) = 0x924f90f43511876e459b2df5976472a479707d65c1b4cf53dfd134d725650d70
```

**5. 錨定：** relayer 呼叫 `AnchorRegistry.anchor(sessionId, merkleRoot, tallyHash)`，其中 `sessionId = keccak256(bytes("6650a3b2c1d0e9f8a7b6c5d4"))`。

驗證工具會用公開的資料集重做第 1 到第 4 步，從鏈上讀回第 5 步的值，再進行比對。

## 為什麼 PASS 值得信任

論證的每一環都建立在一項設計性質上。

### 錨定後，鏈上的值無法更改

`AnchorRegistry` 沒有任何修改或刪除承諾的函式：

- 場次已有紀錄時，`anchor` 會以 `AlreadyAnchored` revert。
- owner 只能更換 relayer 地址，無法碰觸既有紀錄。
- registry 不可升級。重新部署會產生位於新地址的新合約，舊紀錄仍留在原處。
- `timestamp` 與 `blockNumber` 由合約依區塊設定，不是由呼叫者提供。

因此平台的承諾被固定在一個公開、有時間戳記的時間點。要改寫它，等於要改寫 Base 的歷史。

### 驗證工具只從鏈上取得雜湊

metadata endpoint 也會回傳 `merkleRoot` 與 `tallyHash`，但驗證工具會忽略它們。它用 `getAnchor` 讀取承諾，其餘一切都在本機重新計算。它也會檢查 RPC endpoint 是否在預期的鏈上，所以設定錯誤的 endpoint 無法拿另一條鏈的狀態來頂替。如果你不信任預設的公開 RPC，可以用 `--rpc-url` 指向自己的節點。

### 一個雜湊只對應一份資料集

keccak256 具備抗碰撞性：實務上沒有人能找到兩個雜湊相同的不同輸入。所以 `merkleRoot` 一旦固定，唯一能重現它的資料集，就是當初錨定的那一份。任何一張選票的任何改動都會改變它的 leaf，進而改變它上方直到 root 的每一個節點。

標準化讓這件事在兩個方向上都成立：

- **確定性：** 同一份邏輯上的資料集，不論你下載的副本 key 順序、空白或選票順序為何，都會產生相同的位元組。誠實的副本，例如鏡像或封存，一定能通過驗證。
- **無歧義：** 每條規則（排序、移除 0、只允許整數）都只有一種結果。兩個實作不可能對「指的是哪些位元組」產生分歧，否則作弊者就有空間宣稱「這只是另一種編碼」。

### Merkle tree 無法被矇騙

這棵樹的設計避開了已知的 Merkle tree 陷阱：

- **領域分隔（domain separation）。** leaf 的原像以 `c`（來自 `civicue.ballot.v1`）開頭，內部節點的原像以 `0x01` 開頭。內部節點永遠無法冒充選票，反之亦然。
- **不複製節點。** 落單的節點原封不動地往上一層，而不是和自己配對。在會複製節點的樹中，`[a, b, c]` 與 `[a, b, c, c]` 的 root 相同，因此可以多塞一張選票而不改變 root。在這裡兩者不同。
- **投票者編號連續。** `voter` 必須恰好是 `1..n`，每個編號出現一次，leaf 也依此排序。因此選票的數量與位置都被承諾，計票結果中的 `ballotCount` 也必須一致。

### 驗證工具自己計算結果

驗證工具不是檢查平台的計票結果「看起來」合不合理。它會對選票執行投票規則，再把輸出雜湊：

- `MAJORITY` 計算每一個勾選。
- `QUADRATIC` 先排除 Σ 票數² 超過 `voiceCredits` 的選票，再加總票數。
- `RANKED_CHOICE` 逐輪重演即時決選（instant runoff），平手處理規則完全明確。

如果重新計算的 `tallyHash` 與鏈上一致，錨定的計票結果就是這些選票的正確結果。平台若錨定了誠實的選票卻配上不同的結果，即使 `merkleRoot` 通過，`tallyHash` 也會失敗。

計票結果包含了所有決定結果的要素：

- `schemaVersion` 與 `votingMethod`，所以同一批選票無法用其他規則重新解讀；
- 平方投票的 `voiceCredits`，所以預算無法事後更改；
- 排序複選計票的每一輪，包含淘汰與耗盡的選票。

### 版本同時綁定在兩個雜湊中

schema 版本同時出現在 leaf 標籤（`civicue.ballot.v1`）與計票結果（`"schemaVersion":1`）中。宣告不同的版本會讓兩個雜湊都改變（見 `vectors/v1/version-binding`）。因此資料集無法被重新標上較新的版本，藉此套用不同的規則。驗證工具不認得的版本會回報為 UNSUPPORTED，絕不會用猜的。

### 大家看到的結果與錨定的結果綁在一起

人們是在平台上看結果，不是看雜湊。`resultSummary` 檢查會把平台公布的 `result`（勝出者、投票人數、各選項票數）與重新計算的計票結果做精確比對。所以顯示給大家看的數字，不可能悄悄地和錨定的數字不同。

在排序複選中，摘要只列出最後一輪的選項及其最後一輪的票數。完整的淘汰過程並沒有遺失：它是計票結果的一部分，由 `tallyHash` 承諾、由驗證工具重新計算，而且 `--json` 會把它輸出（`recomputed.tally.rounds`）。

### 任何人都能檢查驗證工具本身

- 驗證工具是一個小型、相依極少的 TypeScript 套件。它不會對網路寫入任何東西，也不持有任何金鑰。
- [Conformance vectors](../vectors) 為每種投票方式及其邊界情況固定了確切的雜湊值。平台的 producer 在自己的 CI 中執行同一組 vectors，所以 producer 與驗證工具是兩個必須逐位元組一致的實作。
- 每個步驟都使用標準的密碼學原語，可以用其他工具重現。例如 `cast keccak` 可以從任一 leaf 的標準 JSON 重現該 leaf。
- 任何人只要依據[格式規格](canonical-schema-v1.zh-TW.md)與 [API 規格](verification-api.zh-TW.md)，就能寫出一個獨立的驗證工具。

## 各種竄改會觸發什麼

| 錨定後所做的改動                   | 偵測方式                                              |
| ---------------------------------- | ----------------------------------------------------- |
| 某張選票的選擇被改                 | `merkleRoot`，通常還有 `tallyHash` 與 `resultSummary` |
| 兩位投票者的選票被對調（總數不變） | `merkleRoot`                                          |
| 新增或刪除一張選票                 | `merkleRoot`、`tallyHash`                             |
| 公布的結果與錨定的不同             | `resultSummary`                                       |
| 錨定的結果不是這些選票的正確計票   | `tallyHash`                                           |
| 某張平方投票選票超出預算           | `BUDGET_EXCEEDED`                                     |
| 平方投票的預算或投票方式被改       | `tallyHash`                                           |
| 資料集被重新標上另一個 schema 版本 | `merkleRoot`、`tallyHash`                             |
| 鏈上紀錄被更改                     | 不可能：registry 只能寫入一次。                       |

## 兩個驗證層級

任何人，不論是投票者、記者或稽核者，都可以用兩個層級之一檢查已結束的場次。兩者都只用公開資料。

**第 1 層：結果在公布後沒有被更改。** 用區塊瀏覽器打開場次的 `anchorTxHash`。這筆交易存在、帶有時間戳，而且 registry 只能寫入一次，所以平台在那個時間點承諾了這組 `(merkleRoot, tallyHash)`，之後無法更改。這一層不需要任何工具，但無法證明承諾的結果是對的。

**第 2 層：結果是正確的計票。** 執行驗證工具：

```bash
npx @civicue/voting-anchor-verifier verify --session <id> --network base --platform <platform-api-base-url>
```

它會從公開的選票重新計算 `merkleRoot` 和 `tallyHash`，與鏈上比對，並且把公布的結果和自己算出的結果比對，過程如上文所述。平方投票還會逐張檢查預算，這也是資料集要公開匿名的逐票資料、而不是只公開各選項總數的原因。

| 攻擊手法               | 由哪一層擋下                |
| ---------------------- | --------------------------- |
| 公布後竄改結果         | 第 1 層（鏈上紀錄不可更改） |
| 算錯票，或偷改計票規則 | 第 2 層（公開重新計票）     |
| 平方投票超出預算       | 第 2 層（逐票檢查預算）     |
| 公布前捏造或刪除選票   | 擋不下（見下節）            |

## PASS 不能證明的事

- **公開的選票就是所有真實的投票。** PASS 證明公開的選票沒有被改過、而且計票正確，但不能證明它們是真實的：營運方可以公布一組前後一致的假選票，它一樣會通過驗證。這裡沒有納入收據（inclusion receipt），也沒有投票者簽章，所以選票集合的真實性靠的是營運方的信譽，而不是密碼學。
- **資料集會一直可以取得。** 資料集由平台自己的 API 提供。如果平台不再提供，就無法從這個來源重新驗證。不過完整性不依賴平台：任何副本，例如封存的副本，都能和鏈上的 root 比對（`--dataset-url`）。
- **沒有錨定的場次。** 流局的場次（投票數為 0）沒有選票可以驗證，因此不會錨定，它的 metadata 端點會回傳 `404`。
